Staging Procedure

Test Cron / Notifiche in staging

Procedura pratica e prudente per verificare i job schedulati di Ischia Transfer Service senza toccare dati reali e senza aprire il perimetro a test distruttivi.

Obiettivo Verificare autenticazione cron, env, risposta delle route e log Vercel.
Approccio Prima endpoint innocui o in dry_run, poi review log, poi eventuali step successivi.

2. Endpoint sicuri da testare per primi

  1. /api/cron/vehicle-expiry-check con dry_run: true
    Miglior primo test: nessuna email, nessuna modifica dati, risposta ricca di preview.
  2. /api/cron/sla-check
    Buon test tecnico: verifica auth, query e chiusura corretta; in staging di solito non ha impatto forte.
  3. /api/cron/push-reminders
    Testabile dopo SLA: se non ci sono servizi nella finestra oraria resta innocuo.

3. Env / config da verificare prima

Minimo indispensabile
  • CRON_SECRET
  • NEXT_PUBLIC_SUPABASE_URL
  • SUPABASE_SERVICE_ROLE_KEY
Solo se testi push
  • VAPID_PUBLIC_KEY
  • VAPID_PRIVATE_KEY
  • VAPID_SUBJECT
Solo se testi email
  • RESEND_API_KEY
  • meglio anche EMAIL_TEST_REDIRECT
Solo se testi WhatsApp
  • WHATSAPP_TOKEN
  • WHATSAPP_PHONE_NUMBER_ID
  • WHATSAPP_CRON_SECRET se separato

Supporto utile: controllare anche la route admin di stato sistema e i log delle funzioni in Vercel prima di partire.

4. Come chiamarli manualmente in staging

Sostituisci https://staging.tuodominio.it e YOUR_CRON_SECRET con i valori reali di staging.

Vehicle expiry check in dry run

curl -X POST "https://staging.tuodominio.it/api/cron/vehicle-expiry-check" \
  -H "Authorization: Bearer YOUR_CRON_SECRET" \
  -H "Content-Type: application/json" \
  -d '{"dry_run":true}'

SLA check

curl "https://staging.tuodominio.it/api/cron/sla-check" \
  -H "Authorization: Bearer YOUR_CRON_SECRET"

Push reminders

curl "https://staging.tuodominio.it/api/cron/push-reminders" \
  -H "Authorization: Bearer YOUR_CRON_SECRET"

5. Header / token da usare

Quasi tutte le route usano:

Authorization: Bearer <CRON_SECRET>

Le route WhatsApp accettano WHATSAPP_CRON_SECRET se presente, altrimenti fanno fallback a CRON_SECRET.

6. Cosa guardare nei log Vercel

  • status code: 200, 401, 500
  • durata funzione e timeout
  • messaggi tipo Unauthorized
  • env mancanti: Missing env, Server env missing
  • errori Supabase query
  • errori esterni: Resend, IMAP, WhatsApp Graph API, web push
  • payload JSON finale della response

7. Come capire se il test è riuscito

Successo tecnico
  • HTTP 200
  • ok: true
  • nessun Unauthorized
  • nessun Missing env
  • nessun 500
Nota importante Un test riuscito non significa per forza che abbia inviato qualcosa. Per molte route va bene anche sent: 0 se la query, l'autenticazione e la finestra temporale sono corrette.

8. Endpoint da evitare per ora

  • /api/cron/agency-invoices — scrive fatture e invia email
  • /api/cron/agency-reminders — invia email vere
  • /api/cron/agency-bus-monday — invia email vere
  • /api/cron/poll-emails — può importare email e booking
  • /api/cron/expire-quotes — cambia stato ai preventivi
  • /api/cron/backup — scrive su Storage e cancella backup vecchi
  • /api/cron/whatsapp-info — può inviare messaggi veri
  • /api/cron/whatsapp-reminders — può inviare messaggi e aggiornare servizi

9. Checklist finale passo-passo

  1. Verifica che lo staging punti a DB non produttivo.
  2. Controlla CRON_SECRET, URL Supabase e service role.
  3. Apri i Function Logs su Vercel prima del test.
  4. Esegui vehicle-expiry-check con dry_run: true.
  5. Conferma: 200, ok: true, dry_run: true.
  6. Esegui sla-check.
  7. Conferma: niente Unauthorized, niente query error.
  8. Esegui push-reminders.
  9. Se sent: 0, verifica che la route chiuda comunque con JSON coerente.
  10. Fermati qui nel primo giro.
  11. Non eseguire ancora email, backup, import email, WhatsApp o quote expiry.
  12. Solo dopo review log valuta un secondo round con dati e destinatari test dedicati.
